# AGENTS.md

Instructions for coding agents working on cauri. `CLAUDE.md` is a symbolic
link to this file. Read `CONTEXT.md` for the original brief, the decisions
taken and why; `README.md` for users and operators.

## What cauri is

A visualisation tool for the Cowrie SSH honeypot, built from scratch
(Honeywatch is only a reference for the data model, never a code base to
copy). Three parts in one Go module (`github.com/devleesch001/cauri`) and
one Docker image:

- **ingestor**: reads what Cowrie writes on disk and forwards it, raw;
- **API** (Go, chi): receives ingestor data, stores it, serves the UI;
- **UI** (Vue 3, Vite, TypeScript, Pinia, Vue Router, OpenVue).

Long-term goals: attack statistics and session replay with
asciinema-player. Version 1 lays the foundations; never make these two
harder.

## Invariants

Do not break these without the user's explicit agreement.

**One binary, one image.** Roles are subcommands of `cmd/cauri`: `api`,
`api --ui`, `ui`, `ingestor`, `token`, `purge`, `db-copy`, `download`, `version`. A future all-in-one
binary is a build tag (`allinone`), not a fork.

**The ingestor only decides which recording to send.** It sends each
`cowrie.json` line unparsed, plus the sensor id and an event id
(`protocol.EventID`: SHA-256 of sensor id and line). It reads only what it
needs for that: `cowrie.log.closed` (one per SSH channel, one per command
for many bots) and `cowrie.session.closed`. It sends a recording only for a
session with exactly one channel whose file is its own (not `duplicate`),
as Cowrie wrote it; sessions with several channels send none, and there is
no merging. It waits for `cowrie.session.closed`, an hour at most. The pty
is not the criterion: bots ask for one too. All interpretation of Cowrie
events happens in the API.

**One ingestion service.** Validation, deduplication, projection into
tables and recording storage live in `internal/ingest.Service`. HTTP
handlers only translate requests and map errors; the future all-in-one
mode calls the service directly. The ingestor writes to the `Sink`
interface (`internal/ingestor/sink.go`); HTTPS is its only implementation.

**Public protocol in `pkg/`.** `pkg/protocol` (routes, payloads, ids,
digests) and `pkg/client` are the contract third-party tools may use.
`internal/` is only for internal logic. Changing `pkg/` is changing a
public API: keep it backward compatible or say so.

**At-least-once delivery.** The ingestor saves its position only after the
API acknowledged a batch; `cowrie.json` and its rotations are the buffer.
Event batches are never dropped. The API must stay idempotent: resending
anything (events, recordings) must not change the result.

**Files are identified by inode and fingerprint, not by name** (rotation
renames `cowrie.json` to `cowrie.json.YYYY-MM-DD`).

**Database.** SQLite first (`modernc.org/sqlite`, no CGO): the default,
what the CI tests, what the project is built and tuned for. The bun ORM
lets users choose PostgreSQL instead, so SQL must run unchanged on both: no
PostgreSQL-only features, no SQLite-only functions in queries (use
`CASE`, not `MIN(a,b)`/`LEAST`). Ids are integers generated by the
database; an event's SHA-256 is only a unique column, for deduplication.
Times are integer microseconds (`store.Time`), durations milliseconds.
Times are stored in UTC (SQLite compares them as text). The API is the
only writer, except `cauri token`, `cauri purge` and `cauri db-copy` (into
an empty target only), accepted by the user. `internal/dbcopy` copies
through the bun models, by table in the order of the foreign keys: a new
table or column goes into its list and its model (`TestTablesCovered`,
`TestColumnsCovered`).

**Every key and index is named**, the same in both engines (the user
insists on it): primary keys `pk_<table>`, unique keys
`uk_<table>_<columns>`, foreign keys `fk_<table>_<column>`, other indexes
`ix_<table>_<columns>`, columns joined by `_` in key order. Declare
primary and foreign keys as named table constraints (`CONSTRAINT pk_t
PRIMARY KEY (id)`: in SQLite an `INTEGER` key stays the rowid). A unique
key is a named constraint in PostgreSQL, which names its index after it,
and a `CREATE UNIQUE INDEX uk_…` in SQLite, whose inline unique
constraints get `sqlite_autoindex_…` indexes: both engines then show the
same name. Never leave a name to the engine: `TestKeyNames` checks them
all (migration 00007 renamed the older ones).

**Foreign keys** carry an explicit
`ON DELETE` (`docs/db.md`): projections and events cascade from their
session, a recording's, a GeoIP database's or a network's removal sets
the session's reference to null, sensors are `RESTRICT`ed while they have sessions.
Every foreign key also has `ON UPDATE CASCADE` (the user's rule): a
parent whose id changes keeps its children. Code relies on them
(`Service.ForgetTTY` only deletes the `tty_files` row): keep both engines
and `TestForeignKeyNamesAndActions` in step.

**Migrations.** bun's `migrate` package, one set per engine
(`internal/store/migrations/sqlite/` and `postgres/`, same names, `.tx.up.sql`
and `.tx.down.sql`), embedded and applied when the API starts, logging the
state of the database, the pending migrations and each one run (`store.Migrate`);
`TestSchemasMatch` checks both describe the same schema. A migration that
needs Go (reading JSON, as 00009 does) is registered in `store.Migrate`
for both engines and runs in a transaction. Released
migrations are immutable: add a new file. Design in `docs/db.md`.

**Raw data is purgeable.** `event_raw_data` holds the Cowrie lines (kept
for ever, N days or not at all: `CAURI_EVENT_RAW_DATA_RETENTION_DAYS`
-1, N or 0, 15 days by default; migration 00009 reads it by its former name, `event_data`); nothing
may reference it except its event, and nothing may need it: what the
tables do not hold of a line is kept in `events.data` (`cowrie.Fragment`:
the line without its envelope and its projected fields), read by the
session page and replays, which get the projected fields back from the
tables (`store.GetSession`, checked by `TestSessionAfterRawPurge`): a
session reads the same before and after the purge. Projections point to sessions; client key
exchanges are in `ssh_kex`, once per combination. When projecting a new
field, add it to `cowrie`'s projected list so it leaves the fragment,
and never query `events.data` in SQL: a field worth filtering on gets a
column.

**TTY recordings** are stored as the ingestor sends them (at most one per
session, see above), never modified, in a volume, named by the SHA-256 of
the file (`internal/ttystore`); the database keeps the reference. They
are converted to asciicast at read time (`/api/sessions/{id}/cast`,
`internal/ttylog` → `internal/asciicast`), never at ingestion. Replays
keep the real timing and include keystrokes (`"i"`) and a marker (`"m"`)
per command; `idle_time_limit` is only a header hint. Chapters (each
command and its plain-text output, `/api/sessions/{id}/chapters`) come
from the same recording, with bounded cost and output. So does the
human/bot verdict (`/api/sessions/{id}/verdict`, `internal/verdict`): it
always returns its reasons with their points, and its thresholds stay
grouped there to be tuned. The verdict is also stored per session (for
the list filter), computed in `internal/ingest`: bump `verdict.Version`
with any change of the criteria so stored verdicts are recomputed. The
same reading stores `sessions.shell` (typed in an interactive shell:
input, and no exec command, `ttylog.DirInteract`); bump the version
with any change of it too. A new asciicast version is a new `Encoder`, not a
change of the converter.

**Simulated replays.** `/cast` and `/chapters` serve the stored recording
if the session has one and its file exists. Otherwise (bots, or a file
the operator removed from the volume to limit retention) they are
simulated from the commands (`asciicast.Simulate`): a banner (`### simulated session ###`), 500 ms later each marker, prompt (a shell's:
`root@<sensor>:~# `, `<user>@<sensor>:~$ `, the user that logged in, its
control characters dropped) and command at their real times, no output;
chapters carry `simulated: true` and the UI shows a badge. `cowrie.json`
never holds terminal output, so a simulated replay cannot have any. The
choice is made on read, never stored. A recording whose file is missing
from an available volume is forgotten on that read (`Service.ForgetTTY`:
`sessions.tty_file_id` cleared, `tty_files` row deleted, verdict kept); an
unavailable volume (`ttystore.Available`) forgets nothing.

**Same origin.** The UI calls relative `/api/...` paths: no CORS, no API
URL in the UI. The reverse proxy routes `/api` to the API.

**Authentication.** Ingestors: one revocable token per sensor, bearer
header, only its hash stored, bound to its sensor id. Administration
(`/api/admin`, UI page `/admin`, token management): one password
(`CAURI_ADMIN_PASSWORD`, else generated and logged at start), sessions in
a signed `HttpOnly`/`Secure`/`SameSite=Strict` cookie (`internal/auth`
`Admin`), changes require the `X-Cauri-Admin` header, sign-in attempts
are limited per client with `go-chi/httprate`, the client resolved by
chi's `ClientIPFrom*` middlewares (`X-Forwarded-For` only from
`CAURI_TRUSTED_PROXIES`). UI and read API:
none yet; it plugs in as the `ReadAuth` middleware of `internal/api`,
without restructuring.

**Deployment.** Never invent values of the user's setup (domains, paths,
networks, passwords, runner labels): use documented environment variables
or ask. Containers run as non-root. Traefik is the example proxy of the
compose files, not a requirement, and no proxy middleware may be made
mandatory.

## Commands

Full development setup (local Cowrie, API, ingestor and UI dev server,
PostgreSQL, troubleshooting): `docs/development.md`.

```sh
make init-dev                  # once: UI deps, local Cowrie, dev token (idempotent)
make dev-api / dev-ingestor / dev-ui    # the dev stack, one terminal each (VS Code: task "dev: all")
make test                      # go test ./... (SQLite)
make lint                      # golangci-lint (config: .golangci.yml)
make ui                        # npm ci && npm run build in ui/
make build                     # bin/cauri, static, UI embedded if built

# Optional, when changing SQL: store/ingest/api/auth tests then also run on PostgreSQL.
docker run -d --rm -p 127.0.0.1:55432:5432 -e POSTGRES_PASSWORD=test postgres:17-alpine
CAURI_TEST_PG_DSN='postgres://postgres:test@127.0.0.1:55432/postgres?sslmode=disable' go test -race ./...

cd ui && npm run lint && npm run typecheck && npm run build
cd ui && npm run dev           # proxies /api to localhost:8080 (CAURI_API_URL to change)

docker build -t cauri:dev .
```

Before considering a change done: `gofmt -l .` empty, `go vet ./...`,
race tests (SQLite; also PostgreSQL if the change touches SQL),
`golangci-lint run ./...`, and for UI
changes lint, typecheck and build. For visible UI changes, look at the
result in a browser.

## Conventions

**Go.** Version 1.27.2 everywhere: the `go` directive of `go.mod` (read by
the CI) and the `golang:1.27.2-alpine` build image; change both together.
Standard library first; `log/slog` (JSON); errors wrapped with
`%w`, sentinel errors for the cases callers map (see `internal/ingest`).
HTTP handlers answer with `go-chi/render`: `render.JSON` (after
`render.Status` if not 200), errors with `render.Render(w, r,
errorOf(status, msg))`, request bodies with `render.DecodeJSON`; the API
answers JSON only.
Match the surrounding comment density: comments say why, not what.
Tests that touch the database use `storetest.Run` so they cover both
engines. API tests go through `pkg/client`, which also checks the public
protocol. Ingestor tests use a fake `Sink`; `e2e_test.go` runs the real
chain.

**Cowrie input is hostile.** Attackers control usernames, passwords,
commands and URLs; a compromised Cowrie controls its files. Keep:
`cleanText` (no NUL or invalid UTF-8 reaches PostgreSQL), lenient
per-field parsing (a wrong type empties a column, never drops the event),
`os.Root` and regular-file checks for TTY files, ignored symlinks in the
log directory, size limits (`MaxBatchBytes`, `max-tty-size`), no
`v-html` in the UI.

**Real Cowrie behaviour** (verified on the official image v3.1.2, sample
in `internal/ingest/testdata/cowrie-v3.1.2.json`):
- durations are `duration_ms`; older versions wrote `duration` in seconds;
- a recording's file name and `shasum` hash its input, all but the
  terminal output (Cowrie's `ttylog_inputhash`: the keys typed, or the
  command of an exec channel), not the file: `sessions.tty_log` keeps
  Cowrie's name, `tty_sha256`/`tty_size` come only from the uploaded file;
- Cowrie writes a recording per SSH channel; bots (libssh, often with a
  pty) open one channel per command in a connection, each with its own
  `cowrie.session.params` and `cowrie.log.closed` (sample in
  `internal/ingest/testdata/cowrie-v3.1.2-exec.json`);
- Cowrie keeps one file per input: a later recording of the same input is
  `"duplicate": true` and its file is the first one's, with that one's
  output and times, maybe of another session;
- files are written by uid 999 with umask 0022 (readable by the ingestor's
  own non-root user).
When adding support for an event, check it against real Cowrie output.

**UI.** Components from OpenVue only (`openvue/<component>`, themes from
`@openvue/themes`, icons from `@openvue/icons`); do not switch to PrimeVue
without asking. Every user-facing string goes through vue-i18n
(`ui/src/locales/en.ts` is the typed reference). Filters live in the URL
query, kept per page for the browser session and restored when a page is
reached without any (`ui/src/router.ts`, VueUse `useSessionStorage`). Visual system in `ui/src/style.css`: IBM Plex Sans for the UI, IBM
Plex Mono only for technical values; red (`--c-logged-in`) means only "an
attacker logged in" (a login succeeded; many such sessions open no
shell, so the UI never says "shell" for it). Colours come from the OpenVue theme
(`ui/src/theme.ts`): the `--c-*` variables point to its tokens (`--p-*`),
so that other themes can be added; no colour value in components. Dark
mode has one source, the `app-dark` class on `<html>` set by
`ui/src/colorScheme.ts` (light, dark or system, chosen in the header),
read by the theme's `darkModeSelector` and by `style.css`. Respect dark
mode, reduced motion, keyboard focus, phone widths.

**CI.** GitHub and Forgejo workflows are kept equivalent. Actions are
referenced by their major version tag (`@v7`) and GoReleaser by
`"~> v2"`, so that fixes apply without changes: the user's choice, do not
pin them to SHAs or exact versions. Jobs run on `ubuntu-latest` with the
least permissions (read-only by default). On
GitHub, jobs run on the runner itself: services are reached on
`localhost`; on Forgejo, jobs run in a container: services by name. Both
use the same actions at the same, latest, major versions. On Forgejo,
short names resolve on data.forgejo.org; an action missing there
(goreleaser-action) is referenced by full URL, valid on Forgejo though
actionlint, which knows GitHub only, reports it.

## Way of working

- For a new feature or an architecture change: present a plan (files,
  schema, protocol, steps) and wait for the user's agreement before
  writing code.
- Ask rather than guess when a choice belongs to the user; say so when a
  simpler option exists.
- One commit per coherent step using Conventional Commits (in English):
  `type(scope): description`. Allowed types: `feat`, `fix`, `docs`, `style`,
  `refactor`, `perf`, `test`, `chore`, `ci`. Scopes: `api`, `ui`, `ingestor`,
  `store`, `auth`, `deploy`, `schema`. Include a commit body explaining why,
  not what. Use `BREAKING CHANGE:` in the footer if applicable. Examples:
  `feat(api): add session filtering by attack type`,
  `fix(ingestor): handle corrupted TTY recordings gracefully`,
  `refactor(store): extract database transaction logic`.
- Report what was verified and what was not (for example, the CI cannot
  run locally).
- The user writes in French; code, comments, UI texts and docs are in
  English.
